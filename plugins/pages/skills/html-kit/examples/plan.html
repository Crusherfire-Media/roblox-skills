How it fits

The server owns the streak. The client only shows it and asks to claim, so a player can never grant themselves a reward. `DailyRewardsService` reads and writes the profile through `DataService`, and the panel reads the synced state through `CharmSync`.

Player [user] -> DailyRewardsPanel: opens DailyRewardsPanel -> ClaimReward remote: claim ClaimReward remote [queue] -> DailyRewardsService: validates DailyRewardsService -> DataService: streak and last claim DataService -> Profile store [db]: saves DailyRewardsService -> CharmSync: state CharmSync [cache] -> DailyRewardsPanel: renders

Approaches

Server-owned streak [recommended] | the server decides the day and grants the reward + A player can't grant themselves a reward + One source of truth in the profile - Needs a remote and a rate limit Client-side streak | the client tracks the streak and tells the server to pay + No remote round trip to show the panel - Exploiters can claim every day at once ~ Common in older games; not safe for currency

Risks

Server time decides the day, so a player who changes their device clock gains nothing; specs pin the server clock. Profiles saved before DR-2 have no `Streak` field. The read path treats a missing field as day 0. The panel updates after the `Claimed` signal's deferred handlers run, so specs call `Deferred.settleAsync()` before checking it. Rewards granted on the client drifted from saved data; granting only on the server removed the whole class of bug.

Panel states

Unclaimed

  • Today's tile pulses and shows **Claim**.
  • Past days show a check mark; future days are dimmed.

Claimed

  • Today's tile shows the time until the next claim.
  • The HUD button's badge clears.

Grace window length | Recommended: 20 hours past midnight UTC, so a player who logs in late at night keeps the streak.
